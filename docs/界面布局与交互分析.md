# 鸣潮回合制遭遇测试：战斗 UI 修订分析

日期：2026-10-09。适用范围：由 v0.1.0 冻结基线继续修订的原 试玩网页 与离线程序。

## 结论与边界

这次应更改战斗画面的空间组织，不是给旧底部按钮换一套皮肤。用户给出的图有三层清晰关系：左上正在行动者的大头像、本回合剩余行动头像、下一回合较小头像；指令在当前行动者身旁纵向展开；右侧显示队员状态。底部常驻技能面板必须真正移除，其占用高度归还舞台。

项目继续保持无 BP、固定速度、个人协奏。借鉴《八方旅人》的信息层级和交互位置，不引入其增幅、职业或随机行动规则。敌在左朝右、友在右朝左；所有素材正尺度显示，不能镜像。用户截图仅作为分析参考，不作为程序素材重新打包或分发。

本报告已做：查看用户原始截图像素；只读冻结版 app.js、style.css、index.html、engine.js、parameters.js；逐张实际查看 10 个友方形态待战图和 5 张敌方原图；读取现有 manifest 的尺寸、锚点与动作映射。

本报告未做：运行新版本 UI 的浏览器验收。下述数值是基于已看图与代码提出的实现候选，必须经过最终浏览器实渲染检验，不能把本报告当作截图通过记录。旧版外部 UI 研究材料在本次工作区未找到，因此不把其内容或验证声明算作本次证据。

## 2. 旧实现为何偏离

历史分析基线：v0.1 冻结版（不随本公开源码分发）。

1. index.html 把 timeline、stage-shell、command-panel 作为三个独立纵向块。style.css 桌面规则继续为 command-panel 固定分配 266px；主舞台剩余高度很小。这是仪表盘式测试面板，不是角色旁命令菜单。
2. 同一 CSS 在 1366×768 下令 battle-layout 约 658px 高；扣除 66px 行动条、266px命令区、20px间隔后，stage-shell约306px，再减上下状态栏约58px，实际 Canvas 约248px。在1280×720下 Canvas 约200px。此为代码推算，非浏览器实测。
3. app.js drawUnit 把友方参考身体高限制为 max(42,min(67,H*.135))，配合上述小舞台时常落在42px，导致人物接近小点。Boss仍保持比例，但舞台本身已被控制区压扁。应先释放舞台高度，再选统一正尺度，不是单独扩大Boss塞满旧框。
4. renderQueue() 只把 currentId 与 battle.queue 拼接成姓名＋速度文本块；没有独立当前大头像，没有下一回合层，也没有重复敌人的图形身份标记。
5. renderActions() 平铺全部可用技能。说明只有倍率、少量成本和削盾，title通常仅动作名或禁用原因；治疗、护盾、增益持续、资源获得、形态变化等完整效果不可见。
6. 原生 disabled 按钮既不能键盘聚焦，也没有等价的详细说明入口。玩家往往无法知道为什么不能用、怎样让它可用。
7. 原 right-column 把队伍、敌情、日志一起放进滚动侧栏。关键信息容易在滚动中离开视野；固定大底栏与长侧栏同时削弱战场。
8. stageBounds 使用整张PNG的外框，不能直接当作人物身体边缘来锚定菜单。千咲剪刀、机兵长枪、无冠者羽翼都会把菜单推离角色。

这不是规则引擎全部有问题。原来的选择行动→目标→确认、动作与规则分离、素材覆盖、形态映射可以保留，改的是呈现与交互状态机。

## 3. 桌面空间规格

必须在 1366×768 与 1280×720、浏览器100%缩放下完成一回合，无需整页滚动找目标或确认。建议：

- 顶工具条 40–44px，只保留必要入口。不要新增英雄标题、营销介绍或装饰大卡。
- 顶部行动条 78–86px。
- 右侧队伍栏宽220–236px，4人常态数据完整可见；更长状态说明进检查层。
- 剩余净高给舞台，1280×720时尽量保持约480px以上。
- 底部最多20–26px状态/保存提示，不恢复大控制台。
- 敌方盾/弱点与公开蓄力标志在单位附近或紧凑敌情条显示；详细敌情和历史日志按需展开。
- 根容器用明确的视口高度与 minmax(0,1fr)，而不是使用会把总高撑过视口的 min-height:606px。

以友方身体参考显示78–88px为开始试排，敌方继续共用相同359像素基准。无冠者身体约3.5倍，其完整PNG仍会比身体更宽。不得为让面板好看而把每个敌人按相同包围盒等高。

友军位置候选：场地可用宽高 W/H（不含右状态栏），groundX=W×(0.63+0.035×队内索引)，groundY=H×(0.48+0.11×索引)。相比旧 .69+.064×索引，这为每个角色右侧保留命令通道。该式只是起点，需用4人＋Boss与机兵形态实看，不应机械照抄。

## 4. 角色锚定菜单与碰撞

### 根菜单

按用户顺序固定六项：战斗、技能、防御、道具、交涉、逃跑。宽164–184px，单项高30–32px，总高约200px，字体14px左右。当前项以明亮边框/底纹与指针表示，不能只用颜色。

- 战斗：普通攻击、撬防、等待等现有基本动作。
- 技能：当前角色当前形态的专属技能。形态不合法项可展示但有准确原因。
- 防御：选中后展示持续与解除条件，仍需确认。
- 道具：若本版没有道具规则，保留该根项但明确“本版本未启用”，不能伪装成可操作功能。
- 交涉：映射引擎明确给出的类别，不凭UI创造成功率、对象或规则；鼓舞/挑衅/协商的归属由规则作者统一。
- 逃跑：显示具体是当前角色撤离还是全队逃跑，不用根菜单字面暗示与引擎不一致的后果。

不要把个人协奏强行变成第七根菜单。它仍是每名角色的100点资源，可以从对应队员卡或技能子层打开手动释放，显示释放者和接收者。

### 定位

用单位 ground anchor 和参考 bodyHeight 计算身体右肩附近的位置，不使用带武器的PNG右边。首选候选：

menuX = actorX + bodyDisplayHeight×0.45 + 12

menuY = actorY - bodyDisplayHeight×0.9

将候选约束在舞台safeRect内（四边12px，另外排除行动条与右状态栏）。若右侧不够，依次尝试左側、上侧；上下超出时先作clamp，再用短引线/指针维持与当前者的关联。菜单不应跳到一个永远固定的屏幕角落。

区分三种矩形：PNG完整边界、主体身体边界、交互点击边界。碰撞优先保护当前者身体、选中目标身体和明确敌方弱点/蓄力提示，而不是因羽翼外框很宽就判断所有空地被占用。

按稳定的“静止站位”定位，不随攻击摆动每帧追赶；换行动者、视口尺寸、形态/校准、Canvas尺寸变化时重算。行动演出期间隐藏可操作菜单或明确锁定，避免菜单贴着冲刺中的角色抖动。

技能子层在同一个菜单面板中替换根列表，并提供返回项；不在两侧再堆一串大面板。记录进入前焦点，返回时还原。

### 目标与确认

选择行动后进入目标态，合法目标有场上轮廓/指针及等价DOM按钮。点击场上单位只选目标，不立即执行；AOE一次标出全部实际目标。确认按钮留在同一浮层中且始终可见。

目标态可以把行动列表收为两行摘要，腾出战场；保留“返回行动”和“确认”两个明确入口。单一目标可以自动选中，但仍须显式确认。取消不耗行动、资源或协奏。

## 5. 完整效果说明

说明不能仅为浏览器 title。建议同一个动作详情组件支持鼠标、键盘、触屏，内容来自引擎/参数，不在UI硬编码另一套数值。

每项按有内容的字段显示：动作名；对象/范围；伤害或治疗的完整效果摘要；成本；资源获得；个人协奏获得；削盾条件与上限；施加/移除状态；持续/消耗时机；形态变化；冷却/使用前提；当前禁用原因。数字必须与当前形态、难度和实际规则一致。

建议格式示例（非本项目最终数值）：

“对1名队友恢复生命并施加护盾。消耗丝线60；个人协奏+15。护盾在……前有效。消耗本回合普通行动。”

“防御：承受的……降低……，持续至本人下一次行动机会；等待也会解除。”

禁止只写“倍率2.5 / 消耗60”或“效果以确认时为准”代替完整说明。也不能把动画的三段攻击写成额外三次规则结算。

### 桌面行为

- hover约120ms进入预览，focus立即进入；鼠标快速掠过不需闪整块面板。
- 已选择动作的说明在离开按钮后保留；悬停别项只是临时预览，离开恢复已选项。
- 详情宽280–340px，优先位于菜单上侧或左上，不挡当前者和目标。先测量再定位，对视口clamp，不能靠overflow:hidden截断内容。
- 文本区太长时只允许面板内部滚动，确认区固定可见；不得让整页滚动。
- 用可读的正文13–14px，不把完整说明压成8px。
- 如果没有安全位置，优先收起已不必要的根列表，在舞台上方空区放详情，而不是盖住Boss面部或合法目标。

### 键盘

- ↑/↓切换根项/技能项，Home/End可选；Enter或→进入子层；←或Esc退一级。
- Tab正常移动至目标、确认、其他功能，不应形成无法退出的焦点陷阱。
- root→技能→目标→取消的每一次返回都还原合理焦点。
- 禁用动作使用aria-disabled与执行前校验，以便仍可聚焦读原因；若保留原生disabled，必须给独立可聚焦的说明入口。
- 操作对话框时遵守该对话框焦点；输入框、选择框内不劫持方向键或Enter。
- 正在演出、换当前者、战斗结束、读档、切换编队时清除旧选择与旧详情，防止把A的技能提交成B的行动。

### 触屏/小屏

首次点选可读完整效果，执行只由显式确认按钮触发。没有hover也不能缺内容；长按不是唯一入口。触摸命中区建议至少44px高，可在紧凑视觉行外围增加可触范围。

窄屏允许行动条折成两行、右状态栏变为紧凑队伍条/检查面板，仍保持角色旁命令的视觉指向；极窄时详情可变成小型可关闭检查层，不能又变回永久底部技能网格。超长说明可内滚，确认/返回固定可见。

## 6. 头像的可靠来源和裁取

## 7. 当前与下一回合队列

显示三段：

1. 当前：64px左右，金色边框/指针，含“当前”短标签。
2. 本回合剩余：42–44px头像，间隔6px，顺序与引擎实际queue一致。
3. 下一回合：30–32px头像，间隔4px，与当前队列有12–20px明显间隔。

4v4时，当前1＋本轮剩余最多7＋下轮最多8，在约760px宽内可安排。名字和速度不常驻，放到hover/focus详情与无障碍label。重复敌人需小号1/2/3标识，与目标选择保持一致；不能显示三个无法区分的相同头像。

不要把currentId再次放入本轮剩余区。等待后当前者转入本轮队尾，只出现一次；个人协奏不在普通行动条插入额外单位。

引擎固定速度使基础排序可预测，但下一轮仍取决于死亡、撤离、破盾等当前尚未结算的事。建议标“下一回合·预计”，在详情说明“按当前存活与状态估算，未确认行动可能改变”。若某部分真的未定，显示未定标志，不人为编造顺序。

破盾持续到下一回合末者可显示暗头像＋跳过标识，或明确从可行动预览排除，但不能看似能正常攻击。不要通过复制battle并执行未来回合来预测，也不要调用会推进RNG、状态到期或日志的方法。

此条只承诺“谁可能获得行动机会”，不显示未公开AI技能、未锁定的目标或尚未发生的随机结果。随机目标显示“目标未定”；已蓄力锁定目标才可显示锁定者。

## 8. 与引擎的接口约定

规则作者已同意提供下列只读数据，UI不应另外猜算：

- availableActions条目category使用battle/skills/defense/items/negotiate/escape，中文从P.ui_categories取。
- 完整说明字段包括effectSummary、targetText、cost/gain/concerto及适用的持续、冷却、禁用原因等；具体以实际接口为准，避免因为字段改名空白整块说明。
- queuePreview()不修改状态，不roll RNG，返回当前/剩余/下轮预览及其不确定性。
- enemyIntent扩展description、telegraphText、counterplayText、chargeTurnsRemaining与真实锁定目标。
- 个人协奏0开局、100上限；默认autoAction不代放。ready/gain/buff_used/charge相关事件可以驱动提示，不能反过来由UI提示触发规则。

UI读取这些字段必须保留纯读取性质。仅hover、focus、打开详情、看下一回合不应改变rngState、日志长度、HP、资源、队列、行动次数或存档。

## 9. 实施优先级
